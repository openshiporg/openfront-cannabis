## Major

### QA-022: Every Platform form wipes all its fields when a submit fails
- **Area:** dashboard
- **URLs:** /dashboard/platform/authority (Amend sales rules), /menu (Add product), /cash (Add register). It applies to every form that uses `<form action={fn}>`.
- **Steps:**
  1. Authority → Amend sales rules. Enter version `QA-2026.2` and tax category `QA-STATE` (uppercase). Click "Save as new version". The client shows "Lowercase code, e.g. flower".
  2. Read the "New rule version" field.
  3. Menu → Add product. Fill all 10 fields with an existing SKU (`QA-SKU-001`) and submit.
  4. Cash → Add register with an existing code (`QA-REG-1`).
- **Expected:** the typed values stay, so the merchant fixes one field and resubmits.
- **Actual:**
  - After step 1, "New rule version" is emptied, while the controlled fields keep their values. The next click on "Save as new version" is blocked only by the browser's native "required" bubble.
  - After step 3, every product field is blank (name, SKU, brand, form, both categories, unit, increment, equivalency, price). The error is generic (QA-023).
  - After step 4, both register fields are blank.
  - Receiving's 15-field form uses the same pattern, so a rejected receipt loses the whole manifest entry.
- **Likely cause and files:** React 19 resets uncontrolled form fields after a function `action` finishes, even when it returns an error, and even when the client-side check returned early without calling `formAction`. Files:
  - `features/platform/operations/components/RulePackForm.tsx:45`
  - `features/platform/operations/components/OperatorForms.tsx`
  - `features/platform/receiving/components/ReceivingWorkbenchClient.tsx`
  - `features/platform/operations/components/WorkspaceKit.tsx`
  - `features/platform/fulfillment/components/AllocationQuotePanel.tsx`

  Possible fix: submit through `onSubmit` with `preventDefault()` and `startTransition(() => formAction(fd))`, or echo the submitted values back in the command state and re-seed `defaultValue`. `OnboardingDialog.tsx` already uses `onSubmit` and isn't affected.

### QA-023: Duplicate SKU and duplicate register code give a generic "Not recorded" error
- **Area:** dashboard
- **URLs:** /dashboard/platform/menu, /dashboard/platform/cash
- **Steps:** Add a product with SKU `QA-SKU-001`, or a register with code `QA-REG-1`. Both already exist.
- **Expected:** "SKU QA-SKU-001 is already used by QA Blue Dream 3.5g" and "Register code QA-REG-1 is already in use", next to the field.
- **Actual:** "Not recorded. Check the details and current authority, then try again." Together with QA-022, the merchant loses everything they typed and gets no reason. The round-1 fix (server rule messages reach the operator) covers thrown rule errors only. Unique-constraint failures come back as Prisma text, which `operatorMessage` correctly filters out.
- **Likely files:** the create commands for product and register in `features/keystone/mutations/{inventory,operations}.ts`: check for an existing SKU or code inside the transaction and throw a plain message. Also `features/platform/lib/commandClient.ts:11`.

- **Area:** dashboard
- **URL:** /dashboard/platform/menu

- **Actual:**

  - The edit form only offers name, price, status and eligibility.
  - `amendCannabisProduct` doesn't accept `categoryCode` or `taxCategoryCode`.
  - At quote time `requireTaxRule(pack.taxRules, product.taxCategoryCode, …)` refuses the product. Every product created before a rules change is permanently unsellable, and the only remedy is a new product with a new SKU.
  - The edit form also doesn't expose `publicDescription`, although the mutation supports it.
- **Likely files:** `features/keystone/mutations/operations.ts:231-245` (`amendCannabisProduct`), `features/keystone/domain/allocationQuote.ts:23`, and the Menu product edit form in `features/platform/operations/components/OperatorForms.tsx` with its list in `screens/PrimaryWorkspaces.tsx`.
