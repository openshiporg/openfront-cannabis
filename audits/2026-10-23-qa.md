## Blocker

### QA-001: The public menu can never show a product
- **Area:** storefront
- **URL:** https://openfront-cannabis-production.up.railway.app/
- **Steps:** Complete onboarding. Add a product in Menu. Receive a package. Open `/`.
- **Expected:** a dispensary's day-one storefront is its menu: the products in stock, with prices.
- **Actual:**
  - `publicCannabisMenu` returns `products: []` whatever is in stock. It only returns rows when the runtime capability `storefront.public-live-menu` is on, and `enabledCapabilities` is an empty `Set()` in source, so it is always off.
  - Onboarding sets `storefrontMode: "configured"`, so even the demo lane stays empty.
  - The redesigned grid, filter track, sort track and product page (`/menu/[id]`) therefore can't render a real item in production.
  - The redesign handoff doesn't list this among the known gaps.
- **Likely files:** `features/keystone/domain/runtimeCapabilities.ts:7`, `features/keystone/mutations/public.ts:43-62`. This looks like a deliberate launch boundary, so the owner decides between turning on the live menu (packages are already filtered to saleable, tested and unexpired) and showing an honest "Menu coming soon" state instead of an empty grid.

### QA-003: Onboarding accepts a rule pack the storefront rejects, leaving the store permanently "not set up"
- **Area:** onboarding, storefront
- **URLs:** /dashboard/platform (setup dialog), then /
- **Steps:**
  1. Fill the setup JSON with reasonable values, for example `purchaseLimits: [{category:"flower", channel:"adult_use", maxGrams:28}]` and `taxRules: [{code:"QA-STATE", rateBps:1500}]`. Nothing in the UI tells you the required shape.
  2. Submit. The dialog says "Setup complete." and every workspace shows "Operating".
  3. Save and publish Store Settings ("Saved and published.").
  4. Open `/`.
- **Expected:** onboarding refuses a pack that the rest of the system will reject, with a message naming the bad field. Once it says "complete", the storefront shows the store.
- **Actual:**
  - The storefront shows "Dispensary menu", "Store not set up" and "Menu unavailable", with the name "Dispensary".
  - `publicCannabisStorefrontSettings` returns `businessName: null`.
  - Cause: `publicAuthority()` runs `assertEffectiveRulePack`, which needs `purchaseLimits[].{capacity, categoryCode, window, maxEquivalencyMicrounits}` and `taxRules[].{categoryCode, capacity, basisPoints}`. Onboarding's `validate()` only checks that those arrays are non-empty. The thrown error is swallowed and turned into the neutral "not set up" state.
  - Onboarding can't be re-run ("authority changes require controlled compliance workflows"), and no UI amends a rule pack. **This production install is now stuck in this state** and needs a data fix or a new amend path.
  - Store Settings keeps saying "Published", and its preview shows the store name, so the merchant has no clue anything is wrong.
- **Likely files:** `features/keystone/mutations/onboarding.ts:30-62` (call `assertEffectiveRulePack` on the input inside `validate()`), `features/keystone/mutations/public.ts:10-23`, `features/keystone/domain/cannabisPolicy.ts:37-62`. Also: the storefront should say "unavailable" rather than "not set up" when authority exists but fails its checks. Sales would fail the same way later, because `commerce.ts` runs the same assertion.

### QA-004: Every model page 404s, and the dashboard home says "No lists configured"
- **Area:** dashboard
- **URLs:** /dashboard, and /dashboard/users, /products, /cannabis-licenses, /staff-credentials, /audit-events, /storefront-settings, /customers, /sales (all of them)
- **Steps:** Sign in, before or after onboarding. Open `/dashboard`, any model list URL, or the Models group in the sidebar.
- **Expected:** model cards with counts, and working list pages, as in E-commerce.
- **Actual:**
  - Home page: "No lists configured. There are no data models configured in your admin interface."
  - Every list URL: HTTP 404, with console "Dashboard operation failed (details redacted)".
  - The Models sidebar group expands to nothing.
  - The same `KsFetchAdminMeta` query sent by curl with the same session cookie returns 200 with every list (about 270 KB), so the server-side fetch is what fails. Without a cookie the API returns "Unexpected error." on `adminMeta`, which hints that the server-side request isn't carrying the session.
  - The Barbershop QA found the same failure (its QA-003), so this is family-wide.
  - Knock-on: Inventory package history links to `/dashboard/inventory-events`, which also 404s.
- **Likely files:** `features/dashboard/actions/getAdminMetaAction.ts` (`getCachedAdminMeta`), `features/dashboard/lib/keystoneClient.ts` (`getAuthHeaders`, `redirect:'error'`), `features/dashboard/lib/getBaseUrl.ts`. Also `features/dashboard/screens/HomePage/index.tsx:80-90` should show an error state, not "No lists configured", and `features/dashboard/screens/ListPage/index.tsx:33-35` turns any fetch failure into `notFound()`.

### QA-007: Dashboard times are in server UTC with no zone label; incident and expiry times come back wrong; hydration errors
- **Area:** dashboard
- **URLs:** every Platform page ("As of …"), /incidents, /inventory, /cash, /authority
- **Steps:**
  1. At 4:01 PM Denver time (premises zone America/Denver), open any workspace.
  2. Record an incident with "Occurred at" 10:00 in a browser on America/Chicago.
  3. Receive a package with "Usable through (America/Denver)" 2027-06-30.
- **Expected:** times in the premises zone, with a zone label, and a date that matches what you typed.
- **Actual:**
  - Pages show "As of 10/23/2026, 10:01:37 PM" (UTC) with no zone.
  - The incident lists as "occurred 10/23/2026, 3:00:00 PM".
  - The package shows "Expires 7/1/2027, 1:00:00 AM".
  - Inventory and Receiving throw React error #418 (hydration text mismatch) on every load.
  - Root cause: `formatWhen` passes `dateStyle`/`timeStyle` together with `timeZoneName`. That combination throws `TypeError: Invalid option`, so the code always falls into `catch { date.toLocaleString('en-US') }`, which means the server's UTC and the browser's local zone, with no premises zone. Receiving's manifest line uses another formatter and is correct (4:57 PM).
- **Likely files:** `features/platform/operations/components/WorkspaceKit.tsx:7-13` (drop `timeZoneName`, or use explicit `year/month/day/hour/minute` options). For expiry, show the "usable through" date as a date, not the exclusive midnight instant. The `toLocaleString()` calls in `features/platform/fulfillment/components/*` have the same zone problem.
